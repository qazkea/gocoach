# Gameplay：AI 开发工作流中文上手指南

这是一份按你当前 Pi 配置写的白话使用指南，不是 Matt 原文的逐字翻译。
你不用先学会 27 个技能，也不用自己调度所有子代理。

## 先记住一句话

**先把想做的东西聊清楚，再拆成小任务，让 AI 实现，最后检查和试玩。**

```text
你描述想法
    ↓
主 AI 问清楚需求，和你确定方案
    ↓
把决定写下来
    ↓
拆成小任务，你确认
    ↓
实现 AI 完成一个任务
    ↓
审查 AI 检查，主 AI 验证结果
    ↓
你试玩、提意见，再继续下一个任务
```

不是一开始让 AI 把整个游戏一次性写完。

## 一、你在跟谁说话？

| 角色 | 负责什么 | 已经配置好的模型 |
| --- | --- | --- |
| 主 AI | 跟你讨论、规划、分派任务、整理结果 | Astra high |
| 实现 AI（implementer） | 接收具体任务，写代码和测试 | Astra medium |
| 审查 AI（reviewer） | 独立检查代码有没有问题、有没有偏离需求 | Astra medium |

你主要跟主 AI 说话。它负责为每个子代理编写本次任务说明。
你不用每次再说“请用 medium”。模型配置已经写进项目文件。

这三个角色使用的是同一款模型，只是思考等级和上下文不同，不是三个不同品牌的模型。
独立审查有帮助，但仍可能漏掉问题，不能代替测试和你的试玩。

## 二、先打开正确的项目

在 PiDeck 中，以这个文件夹作为工作目录开启新会话：

```text
D:\code\tmp\gameplay
```

如果使用终端，输入：

```powershell
cd D:\code\tmp\gameplay
pi
```

出现项目配置信任提示时，确认你要加载这套项目配置。
当前在父目录 `D:\code\tmp` 的会话，不会因为子目录里有配置就自动切换过去。

初始化配置已经完成，不需要再次安装，也不用先运行 setup。

## 三、第一次开发，照着这五步来

下面的游戏只是演示，你可以换成自己的想法。
代码框里的 `/skill:...` 是发给 Pi 的聊天命令，不是 PowerShell 命令。
**每一步等上一步讨论和确认完成后再发，不要一次全部粘贴。**

### 第 1 步：说想法，让 AI 先问你

复制这句，再改成你自己的想法：

```text
/skill:grill-with-docs 我想做一个网页俯视角小游戏：玩家能移动，敌人会追过来，玩家能攻击。先帮我把第一版范围问清楚，不要写游戏代码。涉及技术选择时给我推荐，并解释原因。
```

AI 可能会问：

- 电脑还是手机玩？
- 键盘移动还是鼠标移动？
- 自动攻击还是按键攻击？
- 输赢怎么判断？
- 第一版要不要存档、升级、音效？

你不需要懂技术。不会选时可以说：

```text
我不确定，先解释这两个方案玩家体验上的区别，再推荐一个简单的。
```

**你要做的事：**回答问题、决定范围。

**这一阶段结束的标志：**你和 AI 都能说清楚第一版做什么、不做什么，以及怎样判断它能用。

注意：“不要写游戏代码”不代表完全不写文件。这个技能会在讨论中记录已经确认的术语和重要决定。

### 第 2 步：把刚才的决定写成需求说明

讨论清楚后输入：

```text
/skill:to-spec
```

这个命令相当于说：

> 把我们刚才已经确认的事情写下来，作为之后开发的依据。

通常会生成类似的本地文件：

```text
.scratch/first-playable/spec.md
```

`first-playable` 只是功能名示例，实际文件名由本次任务确定。

文件会说明：

- 要解决什么问题、玩家能做什么；
- 已经确定的技术和行为规则；
- 怎么测试；
- 第一版不包含什么。

AI 可能还会与你确认在哪里测试、哪些行为必须验证。这是为了避免之后子代理猜测。

**你要做的事：**看它有没有记错，可以直接让它“用中文概括这份说明，重点列出不做的功能”。

### 第 3 步：拆成能逐个完成的小任务

确认需求说明后输入：

```text
/skill:to-tickets
```

这个命令相当于说：

> 把需求拆成几个做完就能检查的小任务，列出先后依赖，让我确认。

例如：

1. 打开页面能进入游戏场景，玩家能移动。
2. 敌人出现并追踪玩家。
3. 玩家能攻击，敌人受伤并消失。
4. 增加失败和重新开始。

这只是示例，不要求所有游戏都这样拆。

这里不是“先写全部底层，再写全部界面”，而是尽量每完成一个任务，就能看到一个小结果。

任务文件类似：

```text
.scratch/first-playable/issues/01-player-movement.md
.scratch/first-playable/issues/02-enemy-chase.md
```

**你要做的事：**确认拆分和顺序。不合理就说“第一项太大，再拆小一点”或“先不做第四项”。

### 第 4 步：让 AI 开始实现一个任务

最容易的说法是：

```text
按刚才确认的任务列表，先实施第一个没有阻塞的任务。把任务交给 implementer，完成后交给 reviewer 审查，再验证结果。先不要继续下一个任务，也不要推送代码。
```

也可以用明确的技能命令。下面的路径要替换成实际任务路径：

```text
/skill:implement .scratch/first-playable/issues/01-player-movement.md
```

这时主 AI 应当：

1. 读任务和需求说明。
2. 给实现 AI 写具体任务提示词。
3. 实现 AI 写测试、写代码、运行检查。
4. 主 AI 安排独立审查，必要时交回实现 AI 修复。
5. 主 AI 核对实际修改与验证证据，告诉你如何试用。

如果缺少关键决定，AI 应该回来问，而不是擅自加功能。

本项目目前还没有初始化 Git。一般的顺序开发可以先进行；需要提交或并行分支时，由主 AI 说明前提，再由你确认处理。此指南不会自动初始化 Git。

### 第 5 步：你试玩，再决定下一步

你可以说：

```text
告诉我怎么启动、打开哪个地址，以及这个任务需要手动检查哪几项。
```

试玩以后，如果满意：

```text
这一项通过，继续下一个没有阻塞的任务，按同样流程实现和审查。
```

如果有问题，尽量描述操作和现象：

```text
按住右键移动时正常，但松开后角色还会继续走。先检查这个问题，不要扩展其他功能。
```

AI 说“测试通过”不代表画面、手感和所有交互都符合你的预期。游戏仍然需要你试玩。

## 四、什么情况下不用整套流程？

改一个按钮文字、调一个颜色，直接说就行：

```text
把开始按钮的文字改成“开始游戏”，不要改其他行为。
```

不必为这种小改动写一份需求说明再拆任务。

下面这些则更值得完整走一遍：

- 新增存档系统；
- 新增升级和装备；
- 从键盘操作扩展到触屏；
- 一次会影响多个模块的新玩法。

原则是：越容易理解不一致、越难验收的工作，越值得先讨论和记录。

## 五、其余技能什么时候用？

暂时不记它们也可以，先会用前面的四个命令。

| 技能 | 白话含义 | 什么时候用 |
| --- | --- | --- |
| grill-with-docs | 追问需求，同时记录共识 | 还没想清楚功能 |
| to-spec | 把共识写成需求说明 | 讨论完成 |
| to-tickets | 把需求拆成小任务 | 准备安排开发 |
| implement | 实施任务，并组织检查 | 开始开发 |
| tdd | 用先失败、后通过的测试约束实现 | 实现代理工作时使用 |
| code-review | 独立检查需求符合度和代码质量 | 代码写完后，由主代理组织 |
| triage | 整理别人提交的原始反馈 | 开始收集测试者反馈时 |
| diagnosing-bugs | 有证据地定位难查的错误 | 已确认有 bug，但原因不明 |
| handoff | 写交接说明，让新会话继续 | 当前会话太长，准备换会话 |
| retro | 回顾哪里不顺，改善工具和规则 | 一次开发明显费劲、反复出错后 |
| implement-spec | 协调一整批任务实施 | Git 和任务依赖都准备好以后 |
| setup-matt-pocock-skills | 初始化任务和文档约定 | 本项目已经配好，暂时不用 |

`triage` 不是主流程必经步骤。自己刚刚拆好的任务，不需要重新分诊。

想做复盘可以输入：

```text
/skill:retro 回顾刚才的开发过程，指出哪些问题可以通过测试或项目说明避免。先给建议，不自动修改。
```

## 六、想换一个新会话继续怎么办？

先在旧会话输入：

```text
/skill:handoff 下一次继续当前游戏开发，请记录已完成任务、未完成任务、关键决定和下一步，并给我交接文件的完整路径。
```

然后在同一个项目目录开启新会话，把实际路径发给新会话：

```text
读取这个交接文件，并先检查项目的实际状态，再告诉我下一步：这里粘贴交接文件的完整路径。
```

不要只说“继续昨天的”，因为新会话不一定有之前的聊天记录。

## 七、我应该看哪些文件？

| 文件 | 你可以把它当成什么 |
| --- | --- |
| AGENTS.md | 给 AI 的项目导航页 |
| .scratch/<功能名>/spec.md | 你和 AI 达成共识的需求说明 |
| .scratch/<功能名>/issues/ | 每个小任务的说明和验收要求 |
| .pi/agents/implementer.md | 实现代理的固定角色和模型配置 |
| .pi/agents/reviewer.md | 审查代理的固定角色和模型配置 |
| .pi/settings.json | 主会话默认模型设置 |
| .pi/skills/ | Matt 原版技能说明，不必逐篇阅读 |
| docs/agents/pi-workflow.md | 给 AI 用的详细 Pi 适配规则 |

`AGENTS.md` 不会自己执行代码，它让主 AI 知道去哪读规则。skills 也不是点击后必定按固定步骤跑完的程序，而是指导 AI 工作的说明。你随时可以纠正、暂停或缩小任务范围。

通过 `/agents` 可以查看子代理及运行情况。若实际用了错误角色或模型，可以让主 AI 检查配置，不必自己反复写模型名。

## 八、现在不知道从哪开始？只发这一句

在 gameplay 的新会话里输入：

```text
/skill:grill-with-docs 我想做一个小游戏，但还没想清楚。请用中文和我讨论，先问我最影响第一版范围的问题，每次别问太多。不要先写游戏代码，技术问题给我容易理解的推荐。
```

然后正常聊天就行。等想清楚了，再进入需求说明、拆任务、实现和试玩。

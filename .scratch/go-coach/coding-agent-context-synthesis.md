# Coding agent参考：压缩与会话的收口建议

Execution: in-progress（限定资料研究与下述四项产品交互确认已完成；技术规格与实现仍未完成）

## 本轮用户确认结果

- 选择“发送后自动处理”，替换逐模型请求确认：一次提问在明确范围/运行硬限内允许必要压缩和模型续请求，会有额外用量，可停止。
- 用户强调只有聊天提问才生成回答、切手只是浏览；因此切手不生成新回答，也不取消原问题，原回复仍标记发送时的局面。
- 新问题排队，保留点击发送时的棋盘；可以撤回待处理消息、手动停止当前回答。
- 同谱重导先提示继续已有复盘或新建，新建保留旧记录。

以下研究事实仍按其版本/覆盖边界解释；阈值、存储与工具硬限仍待技术规格，不据此运行真实模型、读取Key或恢复被暂停的implement-spec。

## 可以借鉴的事实

1. **工作上下文不等于原文档案。** Claude Code接近窗口时压缩；恢复压缩会话用最后摘要、未摘要部分及后续消息，不会把所有旧消息重新送给模型。[官方上下文](https://code.claude.com/docs/en/context-window)、[会话恢复](https://code.claude.com/docs/en/sessions#what-a-resumed-session-restores)。Codex该版本也将compact结果替换工作历史，并记录压缩事件；所查本地编排分支并非保留近期完整问答，不能逐行照搬。
2. **压缩不是免费字符串裁切，也不是无损记忆。** Claude Code文档明确compact本身是读取历史的大请求；Codex客户端编排摘要也调用模型，不能把“local compact”当离线能力。[官方用量说明](https://code.claude.com/docs/en/costs)、[固定版本compact代码](https://github.com/openai/codex/blob/8272f9a71ee7364d8de992418103628f8a17eb6f/codex-rs/core/src/compact.rs)。DeepSeek接入不能假定支持Anthropic/OpenAI专有压缩协议。
3. **发送时的选择与之后浏览分离。** Claude Code文档说明，生成期间新消息可排队，附带的IDE选区保留发送时快照，不随之后选区变化；中断是另一种操作。[官方输入队列](https://code.claude.com/docs/en/interactive-mode#queue-messages-while-claude-works)。这支持Go Coach按提问时局面绑定回答的思路，围棋产品行为由上面的用户确认另行确定，而非由外部文档代替。
4. **会话恢复不等于工作执行恢复。** Claude Code恢复时，中断的工具不会自动重跑；fork另建会话ID。Codex该版本也区分thread身份、存档、工作上下文与当前任务。它们不能替本项目定义“同一盘棋”，也不能证明重新打开后应后台续发请求。
5. **压缩失败仍须有终止条件。** Claude Code有压缩后大输出反复填满窗口而停止的thrashing保护。[官方故障说明](https://code.claude.com/docs/en/troubleshooting#auto-compaction-stops-with-a-thrashing-error)。不能承诺任何输入都能无损压缩继续，也不能无限循环摘要。

## Go Coach方案方向（交互按上文确认，技术细节待规格）

### A. 压缩

正常长度按序保留对话；接近实际模型窗口时整理已结束的早期讨论。候选工作窗口为固定规则、早期摘要、近期完整问答、当前问题/棋盘快照和必要工具/资料结果。当前问题及未完成工具调用不被摘要悄悄吞掉，工具调用与结果保持合法配对。

摘要记录已讨论问题、结论及不确定性、未解决事项、原消息和手数/分支引用；它只是历史描述，不认证棋理或让过期分析复活。原文独立保存，可回查。失败不提交半成品替换、不删原文、不自动反复发摘要请求。具体阈值、计数、保留区间及失败重试策略还需技术规格和真实业务测试，不照搬别人的百分比。

### B. 本地变化补查

这相当于coding agent为回答问题主动读文件/跑检查：教练用已有依据回答；若用户问的另一落点/变化尚未覆盖，则请求棋规与本地引擎检查额外局面。它不同于RAG查教材、原文回查或网页搜索。工具核验合法性、当前局面身份和分析条件，结果仍可能只是有限搜索估计，不能当死活证明。

既有用户许可是少量自动本地补查；具体工具、次数/时间/长度硬限仍待定，不能说已经有无限自动搜索。取消费用预算不取消这些运行边界，也不允许现在运行真实KataGo。

### C. 会话与在途回复

建议：
- 浏览另一手不改已发送问题的快照。问第45手后翻到80手，原回复仍标第45手，不自动跳回棋盘，也不自动替用户问80手。
- 新问题记住点击发送时的局面并排队；提供明确停止入口。用户已选择排队，没有选择新问题自动打断旧回复。
- 重导相同棋谱先提示“继续已有复盘 / 新建复盘”，不静默合并或打开旧聊天。棋谱内容身份只是匹配线索，不替代稳定会话ID。
- 切换另一盘或退出时不继续为旧盘启动新模型请求；尽力取消在途请求并保留中断状态。已发出的远端计算不保证撤销；恢复不自动重发。

### D. 已完成的授权交互选择

研究前的决定是**每个新增付费模型请求预览确认**，不能只凭“参考coding agent”自行覆盖。主代理随后明确提出下面两种产品模式，用户已经选择第1种：
1. 点击发送后，允许本次问题在明确范围/运行硬限内完成必要的摘要、工具后续模型请求；不再每个请求弹窗，可停止，不因浏览/启动/恢复自动发问。会有额外模型用量。
2. 保留逐个模型请求预览/确认，包括摘要和工具后续调用，一问可能多次确认。

这只是将来的软件交互选择，任何选择都不授权代理现在读取真实Key、上传私人棋谱或实际收费。金额预算、月度额度与费用账本已取消，不重新引入。

## 2. JSON、输出上限及 usage

### 2.1 JSON 不等于严格 schema

- **事实：[JSON Output 指南][S5]**承诺“valid JSON strings”；[S3] 的 `response_format.type` 只列 `text` / `json_object`，**不是 `json_schema`**。还要求 system/user 消息指示生成 JSON，否则可能一直输出空白至 token 上限；`finish_reason="length"` 时内容可能被截断。
- **结论：Chat Completions 的 JSON 模式仅保证正常完成时的 JSON 语法方向，不保证本项目字段、类型、枚举、坐标或围棋事实。** 必须解析后做本地 schema 和棋局事实校验；截断/拒绝/空内容/网络失败均不得当作成功讲解。不要用无预算的自动重试“修复”。
- **事实：[工具调用指南][S6]**另外提供 `strict` Beta：baseURL 为 `https://api.deepseek.com/beta`，所有 function 设置 `strict:true`；服务器检查支持的 schema。对象属性必须全部 `required` 且 `additionalProperties:false`；不支持字符串 `minLength/maxLength`、数组 `minItems/maxItems`。这是**工具参数的受限 schema**，不是普通 JSON Output 的保证。
- **新核验事实：[Responses API 参考][S11]**现在列 `text.format` 的 `json_schema`：`{"type":"json_schema","name":...,"schema":...}`，文字为“structured output conforming to the given JSON Schema”；[S10]称 `format` fully supported。**不能笼统声称 DeepSeek 所有接口都不支持 schema。** 但本次文档未明确其完整 schema 子集、与 Beta strict 的关系和所有失败例外；也未执行测试。此能力不自动适用于 Chat Completions，不能据此取消本地校验或宣称任意 schema 严格保障。若改用 Responses，需单独确认与验收。

### 2.2 输出限制

- **事实：[S2]**当前两个模型上下文标为 **1M**，最大输出 **384K**。
- **事实：[S3]**Chat Completions 参数是 `max_tokens`，取值 **1–393216（384K）**；输入与生成总长度受上下文限制。未设置时非思考默认 **8K**、思考默认 **64K**、`reasoning_effort=max` 时默认 **128K**。短引文：“The maximum number of tokens that can be generated in the chat completion.”
- **建议：**本候选若以后获准实施，显式限制 `max_tokens:2000`，不要依赖8K默认值；这是费用算例的限制条件，不是现有实现或已授权配置。2000 token 不等于2000汉字，可能装不下完整结构，须允许安全失败。
- **事实/推断边界：**[S11]对 Responses 的 `max_output_tokens` 明说包含“both the visible output tokens and the reasoning tokens”；[S3]只写“generated”总量，未同样逐字说明 Chat 上限与思维链合计关系。结合 reasoning 属于 completion breakdown，可合理推断 Chat 也以生成总量控制，但**未通过真实接口验证，不能把跨接口推断作为开启思考后的硬预算证据**。本候选保持非思考。

### 2.3 计量字段与流式限制

**事实：[S3] 响应 schema（readable 提取缺失时，本次已检查同一公开文档原始 HTML）**：

| 字段（均在 `usage` 下） | 官方含义/关键引文 |
|---|---|
| `prompt_tokens` | 输入总 token；“equals prompt_cache_hit_tokens + prompt_cache_miss_tokens” |
| `prompt_cache_hit_tokens` | 命中缓存的输入 token |
| `prompt_cache_miss_tokens` | 未命中缓存的输入 token |
| `prompt_tokens_details.cached_tokens` | 与 `prompt_cache_hit_tokens` 相同，不能重复累加 |
| `completion_tokens` | 生成的 completion token 总量 |
| `completion_tokens_details.reasoning_tokens` | completion 的细分，“Tokens generated by the model for reasoning.” |
| `total_tokens` | `prompt + completion` |

[S3] 当前流式说明：最后一个内容 chunk 带整个请求的 usage，**不是另外发送 usage-only chunk**；`include_usage:true` 时此前 chunk 的 usage 为 null。断流可能拿不到最终 usage，不能据此认定免费或直接释放预算。该流式行为未实测，建议初期非流式以减少接入复杂度。

[S12]：“actual number of tokens … based on the model's return”；中文字符与 token 的换算仅为粗估。3000 输入须包含系统提示、棋局证据、JSON说明、历史等所有输入，而不仅是用户提问。

## 3. CNY 价格、缓存与思考费用

### 3.1 当前官方单价

**事实：[价格页][S2]，单位人民币元/百万 token；不沿用旧新闻截图或旧报价。**

| ID | 时段 | 输入缓存命中 | 输入缓存未命中 | 输出 |
|---|---|---:|---:|---:|
| `deepseek-flash` | 高峰 | 0.04 | 2.00 | 8.00 |
| `deepseek-flash` | 空闲 | 0.02 | 1.00 | 4.00 |
| `deepseek-v4-pro` | 高峰 | 0.30 | 9.00 | 27.00 |
| `deepseek-v4-pro` | 空闲 | 0.15 | 4.50 | 13.50 |

- [S2] 高峰为**北京时间周一至周五、不含中国法定节假日，09:00–12:00、14:00–18:00**；其余含周末/法定节假日全天为空闲；“空闲时段价格为高峰时段价格的一半”。跨时段长请求具体如何归属本次未明确核实，因此保守统一用高峰价。
- [S2]：“模型调用费用 = token 消耗量 × 模型单价”；充值和赠送余额并存时优先扣赠送余额；价格可能调整。表中没有按非思考/思考另列不同 token 单价。
- **思考费用（文档事实 + 计费推导）：**reasoning token 是 completion/output 的细分，见 [S3]、[S10]；因此按价格页的输出总量规则，应将思维链纳入输出费，**不是免费，也不是在 completion 总量之外再重复加一次**。未发现额外独立“思考服务费”一栏；这不等于保证未来无变化。启用思考或工具循环会扩大输出/回传输入，本笔记算例不覆盖。
- [S4] 带 `tools` 的思考请求需要回传历史 `reasoning_content`，且会拼入上下文；不带 tools 时无需回传，传入也忽略。因此不能只数可见中文解释来估计思考模式成本。
- [S2] Search / Fetch 是另行按成功请求收费的 API（各 ¥5/1000 次）；本候选**不启用**搜索、抓取、文件、图像或工具循环，算例不包含这些服务。

### 3.2 缓存不保证，也不等于零留存

**事实：[上下文硬盘缓存][S13]**：“对所有用户默认开启”；“每一个请求都会触发硬盘缓存的构建”；命中需完整匹配缓存前缀单元。缓存系统为“尽力而为”，不保证100%命中；不再使用后自动清空，“时间一般为几个小时到几天”。

**结论：**以下“无缓存”是**计费保守假设：全部输入缓存未命中**，并不是已关闭服务端缓存。没有核验到关闭所有缓存的可依赖方式；“几小时到几天”只是缓存说明，不是日志、备份、训练副本或所有 API 数据的删除期限。价格页未另列该隐式缓存的创建/存储费，本次不承诺永远无额外费用。

### 3.3 同口径算例（推算，不是报价承诺）

假设：纯文本、非思考、每次**总输入3000 + 总输出2000 token**、100次；每次一次请求、无失败重试/额外轮次/付费工具，所有输入按未命中计费、所有请求按高峰计费。

```text
输入总量 = 3000 × 100 = 300000 token = 0.3 百万
输出总量 = 2000 × 100 = 200000 token = 0.2 百万
Flash = 0.3 × ¥2 + 0.2 × ¥8 = ¥2.20（¥0.022/次）
Pro   = 0.3 × ¥9 + 0.2 × ¥27 = ¥8.10（¥0.081/次）
```

这是该 token 假设下对时段/缓存的保守算例，**不是所有成本的上界**：逐手请求可能远超100次；长历史、重试、超时已发生的推理、并发在途、价变、共享账户其他调用都可增加费用。未核实最低充值额、支付手续费、价格含税口径或平台可设置的月硬限额；不擅自额外加税，也不把赠金当预算保证。需先有本地预留/对账/停用方案，未知收费锁定、不得盲目重试。**不保证50元足够，不保证语义或教学质量。**

### 4.2 API 训练用途：不可声称默认不训练

- **事实：[P2] §4.3**：“我们可能会将服务所收集的输入及对应输出，用于模型训练和服务的优化”，前提为加密、严格去标识化且无法重新识别特定个人，并包含全球免费非排他许可；随后提供关闭“数据用于优化体验”的退出表述。
- **事实：[P3] §一.2“智能对话”**也有类似训练与产品内开关条款；§六.2.1给的是头像→设置→数据管理的交互路径。§一.3“开放平台服务”主要列认证、邮箱、交易信息，**未明确另行承诺 API 输入/输出不用于训练**。
- **事实：[模型原理与训练说明][P4] §二.2**：“少部分数据的构造可能会基于用户的输入”，并说明去标识化、匿名化及退出权利；没有给 API 专属排除保证。
- **审慎结论（推断）：**通用协议覆盖API，又被开放平台协议引用，不能把训练条款当作与API完全无关；在未得到更明确 API 专属书面说明前，应按**存在训练/优化使用风险**处理。也不能仅凭这几段断言每一次API请求都会用于训练。
- **待确认：**API 默认是否用于预训练/微调/优化/人工审核；聊天开关是否覆盖同账户 API、企业账户和下游终端用户；是否存在 API 专属退出、零训练或数据处理附约；关闭后对历史数据/备份/已训练模型有什么影响。**聊天端关闭开关不构成已经核验的 API 承诺。**

### 4.3 留存期限与处理地区

- **事实：[P3] §五.1**：境内运营收集产生的个人信息“存储于中华人民共和国境内”，“目前，我们不会将上述信息传输至境外”，如跨境会遵守规定/征求同意。这是限定范围的个人信息存储说明，**不是所有API内容、所有调用来源及推理处理节点的精确地域承诺**。
- **事实：[P3] §五.2**：仅在提供服务目的所需期间保留；删除/注销/超过必要期限后删除或匿名化，但法律留存及财务、审计、争议等例外可延长。引用网络日志“不少于六个月”。**六个月不是所有API输入输出的统一保留期，也不是六个月后必删。**
- **事实：[S13]**仅给缓存一般几小时到几天；[S10] Responses 是无状态，`store` 不支持、响应固定 `store:false`，缓存自动管理，`prompt_cache_retention` 不支持。
- **结论：**无状态或 `store:false` 只能说明该接口的会话持久化能力，不能推出安全日志、训练用途、备份及缓存全为零留存。
- **待确认：**API原始prompt/输出、安全审核日志、计费日志、缓存、备份各自的最短/最长保存期和删除路径；删除完成时限及法律保留例外；API实际推理/存储地区、境外调用情形、受托处理方/人工访问范围。未找到 API 全量数据固定天数或零留存保证，不自行填入“30天”等其他厂商数字。

### 4.4 本项目职责（事实与建议分开）

[P1] §3.5要求开发者告知下游用户个人信息规则，对委托DeepSeek处理取得同意或其他合法基础；§4.1要求输入具备权利/许可，不涉及国家秘密、商业秘密等；§3.7/§8.1要求AI生成标识并提示可能有错；§7.4不保证准确性/实用性。

**项目建议：**即使后续获准外发，也只发送用户批准的最小局部棋盘/着手和 KataGo 证据，不默认发完整SGF、姓名、账号、赛事元数据或聊天历史。DeepSeek不能替代 KataGo 的棋局分析，不应凭空编造变化/胜率/棋子关系。字段正确、中文流畅或官方通用benchmark都不能证明围棋教学合格；需另行授权后的有限评测和真人验收。

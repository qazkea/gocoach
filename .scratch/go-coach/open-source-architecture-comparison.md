## 1. 先分清三种产品

| 维度 | GoAgent | kgteach | Kifu-Sensei |
|---|---|---|---|
| 定位 | 会调工具的桌面教练 | 给外部教练用的围棋工具箱 | 生成棋谱评论的Web流水线 |
| 主要栈 | Electron、React、TypeScript、electron-store | Python≥3.11，CLI/stdio MCP，运行依赖列表为空 | React/TS、FastAPI/Python、SQLModel、SQLite或PostgreSQL |
| 谁决定下一步 | 模型在本轮工具循环中选择 | 外部LLM宿主/调用者 | 固定程序流程 |
| 引擎连接 | 本地进程，也有远端路线 | KataGo JSONL子进程，可选Unix daemon复用 | 外部KataGo HTTP服务，包装器不在已读核心中实现 |
| 聊天记忆 | 本轮工具messages；聊天有存档但跨用户轮不回灌 | 不提供聊天 | 存评论作品，不是聊天 |
| 知识增强 | 本地关键词、规则与局部棋形匹配 | knowledge hooks是待检索描述，不是检索命中 | 局面特征检测与提示组装，不是教材RAG |
| 最有价值的借鉴 | 工具循环及实战点强制搜索 | 候选级未知、合法性与估值分开 | 可核验事实/引擎估计/启发式解释材料层 |

三者并未证明“围棋教练必须引入向量数据库或通用Agent框架”。同样，检索命中与模型生成流畅都不能证明当前棋局解释成立。

## 2. GoAgent：最接近桌面目标，但连续性没有接完

```text
棋盘/聊天 → IPC → 本轮教练运行器 → 模型
                               ↔ 棋谱、KataGo、棋盘图、知识、画像等工具
                               → 报告与UI消息 → 本地会话存档
```

优点：真的存在模型→工具→结果→模型的闭环，不是提前拼好一段提示；能取棋盘图和局面资料；对实战点有从同一落子前局面强制搜索的路径；界面、发布、画像、报告形成完整产品框架。与本项目同属Electron/React/TS，潜在复用不必跨语言。

关键代价：

- **存档不等于记忆**：renderer提交当前问题，runtime每次建立新的system＋当前任务messages。恢复会话只恢复UI消息；已追调用链没有把旧聊天交给下一轮模型。学生画像不是“刚才那手”的会话上下文。
- **试下接线不一致**：renderer hash为8位hex，main hash为16位hex且材料不同；UI严格比较。按这条源码路径，正常新试下的分析会被当作不匹配。缺预取时教师分析工具又回到主线分析入口。具体UI表现及混入回答仍需另行运行验证。
- **任意指定点补查尚非现成功能**：`katago.compareMoves`只筛已有候选；强制搜索实战点的机制不能等同于任意新落点都会被补算。
- **权限和成本不是我们的边界**：OpenAI-compatible入口提供全部注册工具，包括文件/Shell；Codex入口另有领域白名单，不能混为一谈。12轮不是12次请求的硬上限，修正与重试另计。不是逐请求付费批准/预算账本。
- 核心运行器依赖全局设置、存储与截图IPC，不能复制一个函数就得到独立模块。棋规、分析身份及缓存也有边界，不自动等价于本项目现有可信证据。

结论：三者中，它最值得作为完整桌面产品/分叉候选评估，但不能据现状认定已满足连续追问、可靠自由试下和费用控制。局部借鉴工具/数据组织比原样移植执行权限更可控；完整替换并未被研究预先排除。

## 3. kgteach：分层工具箱，而非现成教练

```text
外部Agent → CLI或MCP → SGF/棋规/教学服务
                     → KataGo运行器/缓存 → 结构化JSON → 外部Agent讲解
```

优点：服务与引擎运行器分层；输出结构化；未分析候选可显式null；本地合法性检查与引擎估值区分；没有自身模型token费。适合给已有宿主补围棋工具，或者借鉴协议。

关键代价：

- 不负责任务规划、聊天保存、上下文选择、教材检索和费用批准；这些仍要由宿主实现。
- 部分教学CLI直接请求第t手落完后的局面，却把候选与第t手实战对比。要评价第45手本方可选什么，应基于第44手结束时，而不是第45手后的对手应手。rank_compare另有正确的t−1路径，不覆盖普通比较。
- 分支起点重放只返回棋盘，丢弃末手形成的简单劫状态；局面fingerprint只有棋盘尺寸与手数；零贴目会被`or 6.5`改写。这些是已读源码的具体缺口，未运行反例。
- 进程取消/迟到响应与Windows daemon有额外验证成本。CLI可用性和Unix daemon支持应分开看，不能笼统断言Windows整体不可用。

结论：最有价值的是“未知也要结构化”的协议思想，而非把这套合法性/分析身份当可信核心。引入完整Python层会增加分发、跨语言契约与引擎所有权协调；若只借协议，不必再加一套运行时。

## 4. Kifu-Sensei：解释材料层最值得研究

```text
上传SGF → 低预算全盘扫描 → 筛重点手 → 精查手前/手后
         → 棋盘事实与启发式检测 → 组织PV/ownership等材料
         → 每手一次Claude请求 → 评论/带注释SGF存档
```

优点：确定流程容易检查；先筛重点减少模型请求；前后turn配对及缺结果有保护；单条评论失败可保留其他成果。更重要的是它不只把胜率丢给模型，而是先计算打吃、连接、提子等可解释信息，再组织提示。检测器与网络分离，具备局部移植与契约测试价值。

关键代价：

- 没有连续聊天、主动补查工具环或本盘问答召回；评论历史不是聊天记忆。它解决“生成一份复盘作品”，而不是“与同一盘棋连续讨论”。
- 推荐来源在手前局面，配对方向正确；但没有为实战/推荐建立等条件、等搜索量的两条反事实分支，也不等于我们想要的自由试下对照。
- 部分基于ownership阈值的“安定/濒死”标签继承EXACT，提示却允许把非estimated行当事实。这是上游材料分级问题，不是模型多加一句“不要幻觉”就能补救；不代表已经实测模型必然误教。
- Web后端、数据库和KataGo HTTP服务增加部署与托管边界；API key是服务器加密保存而非桌面OS凭据。批量调用没有逐请求确认；停止观看不等于取消后台生成，重启将任务标失败而非续跑。

结论：适合愿意接受服务器/BYOK/批量复盘的产品路线。对本项目更独特的增益是解释材料组织和测试思路，不是它的账号服务器、任务队列或Claude批量调用循环。当前本项目尚无ownership输出，借鉴相关检测器还需扩展证据与分析预算，不能当现成功能。

## 5. 对上下文设计的启发（仍是候选）

三件事不能互相替代：

1. **本盘记忆**找回“第45手你刚才说了什么”：消息、手数/分支锚点、原文检索与实际请求组装。
2. **领域工具**回答“如果走这里会怎样”：完整局面、合法性、同起点比较、限额内本地分析及有效证据。
3. **解释材料**约束“凭什么说这是打吃/危险/厚势”：可复算事实、引擎估计、启发式与教材概念分别标注，不能把相关性当原因。

若继续当前项目，可考虑借GoAgent的受限工具循环、kgteach的未知协议、Kifu-Sensei的解释材料分层；保留已有棋规、证据校验、OS凭据及待实现的预算边界。但没有选定框架、知识库或实际外发历史；“近期＋原文索引/检索、暂不加远程embedding”仍只是候选，不因完成研究而自动批准。

若转向完整产品分叉，GoAgent是三者里与桌面目标最接近的候选；先验证旧话题追问、试下回收与回主线、跨棋局同手数、逐次请求授权，才能比较修复成本与继续自建成本。尚未进行这类运行验证，也不给工期或质量保证。

## 6. 许可与质量门

三者主代码根LICENSE均为MIT，但数据/模型/资产不能随之视为MIT。GoAgent定式来源清单明确将Pachi资料标为随包GPL-2.0-only，Josekle为MIT，Kogo未随包并要求分发许可；这里只核实其清单，未全量追溯上游版权。

测试能证明什么须分层：GoAgent部分关键接线测试仅正则匹配源码；kgteach假流/教学样例不会自动发现真实引擎局面错位；Kifu-Sensei程序测试约束材料生成，但不证明术语标签等于可靠棋理。三者有价值的测试都可参考，不能由测试文件存在推出真实教学已验收。

本研究结束于架构比较，不改变当前设计/外发/费用授权状态。下一步由用户决定继续讨论哪条路线或是否另行授权隔离验证。

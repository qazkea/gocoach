# 连续复盘上下文与自动补查：设计讨论记录

Execution: in-progress（16已验收；用户现已批准17–22六片图及限定本地提交/多代理隔离实施。本文保留讨论脉络，现行实施要求以spec.md、implementation-plan.md及对应任务/设计为准。）

本文件补充已确认的[界面简报](ui-design-brief.md)，后续与[08B草案](08B-design-draft.md)对齐。最新决定已撤销费用预算门槛；隐私、凭据隔离和发送授权仍保留，旧预算草案不能直接派发。

## 新确认的功能政策

- 用户允许教练围绕当前问题**自动补查少量本地变化**，不要求每次本地补查先手动点击。具体工具、次数、时限及分析预算仍待设计；不是无限自动搜索，也不是允许代理现在运行用户引擎。
- 原谱不被修改；用户在coding agent研究后已改为“发送后自动处理”：未来产品中，发送一个问题授权该问题在明确字段范围和运行硬限内的必要压缩、工具后续模型请求，不再逐请求弹窗。此开发选择不授权代理现在读取真实Key、外发真实数据或消费。
- 用户在研究后的讨论中明确：**chatbot是主体，围绕同一盘棋的连续对话是主线**；围棋理解/分析能力再通过RAG、Skill等方式组织。此确认是产品定位，不等于选定某框架、模型或具体技能实现。
- 用户质疑“旧话题按需找回”作为默认方式不像chatbot；此前“近期窗口＋旧话题检索”从未获最终确认，不作为首版默认方案。正常连续对话按顺序保留历史，仅在接近模型上下文容量时压缩较早内容，不靠检索偶然找回前文。
- **新增文本/历史的开发字段范围已确认，产品改为按本次提问授权。** 已选范围：当前问题、本盘对话、当前棋局必要信息及有效分析、用到的资料与教学方法；范围须明确展示，用户发送问题后允许范围内的必要模型请求，不再逐请求确认。不自动附带原始SGF、姓名、注释或文件路径；自由文本仍可能含私人信息，不能声称自动匿名。窗口压力按下述压缩政策处理，不再按费用预算暂停。此确认不是现在读取Key或真实外发/消费的许可，也未批准远程embedding。

## 最新交互确认：coding agent研究后的收口

用户已完成本轮选择：

1. **发送后自动处理。** 明确替换先前“每个模型请求都预览确认”的产品方案；一次问题可以包含必要摘要与工具后续模型请求，会产生额外用量，可停止。授权只覆盖该问题的明确字段范围/运行限制，不扩展到任意文件、URL、其他棋局或新供应商。
2. **聊天才触发回答，切手只是浏览。** 用户强调“就聊天才会生成回答吧？切手可能就是浏览啊”。按此区分：切手不自动提问或生成新回答，也不取消已发送的原问题；回答仍绑定提问时的手数/分支，不冒充后来浏览的局面，不自动把棋盘跳回去。既有本地整局扫描/棋局分析与生成聊天回答是不同流程。
3. **新问题排队。** 记录点击发送时的局面，等待前一问完成后处理；待处理消息可撤回，可手动停止当前回答，不把后来的问题悄悄混进旧回答。
4. **同谱重导先提示。** 识别已有记录后，让用户选继续已有复盘或新建；新建保留旧记录，不静默合并历史。会话与棋谱身份分开，技术上的同谱判定仍需在规格中明确。

以上产品行为已确认。用户随后批准17–22任务图、本任务本地提交及多代理隔离实施，解除新应用实现暂停；具体接口/存储/压缩设计由主代理按现行spec收口，运行硬限已有工程初值。真实Key读取、真实服务调用、私谱外发、实际消费及本轮真实GPU运行仍未授权。

## 最新范围调整：取消费用预算，增加上下文压缩

用户明确指出长对话应做上下文压缩，随后说明“就是超出窗口，然后没有超出预算这一说，不要预算”。该决定覆盖此前“超出窗口或预算先暂停”的选择：

- 取消应用¥50/月上限、金额预留、预算不足停用及为此设计的费用账本/跨月恢复。费用预算SQLite worker预检不再阻塞聊天接入；若以后为会话存储选择SQLite，其打包与存储可靠性仍须独立验证。
- 上下文接近模型容量时进行压缩，而非一到窗口就默认结束聊天。具体阈值、计数、摘要模型/方法和失败恢复尚待设计；需给输出和必要工具结果留出空间，不能等超限后再把整段超长历史直接发给摘要模型。
- 候选工作上下文为：固定规则＋较早讨论摘要＋近期原文＋当前问题＋明确的当前棋盘/分支及有效依据＋必要资料。摘要保留讨论目标、已确认选择、未解决问题及原消息/手数/分支引用；不能把旧回答、摘要或过期依据升级成当前棋局事实。
- 完整聊天原文仍在本机保存，压缩只改变发给模型的工作上下文，不删除原记录；需要原话或细节时可回查。正常长度不预先裁成近期几轮。
- 取消的是费用上限，不是取消模型输出上限、引擎计算资源限制、取消/幂等和工具循环约束。当前deepseek-flash非思考、max_tokens=2000选择不变。
- 取消费用预算时曾保留逐次确认；后续用户又明确选择发送后自动处理，现已覆盖逐请求确认方案。压缩的额外模型请求须属于本次提问的授权范围；开发同意不是现在读取真实Key或实际收费的许可，也不将摘要描述为免费。
- 压缩失败或单条输入过大仍需诚实提示，不静默丢弃关键内容；这属于容量/可靠性失败，不是费用预算不足。

本节是已确认方向与待细化实现边界，不代表压缩功能已实现。

## 已核对的现有代码事实

主代理在只读定位后复读了`server/evidence.ts`、`src/EnginePanel.tsx`、`src/evidence.ts`，并对照15设计：

- 服务端证据保存完整规范前缀及有界候选/PV，按完整历史、规则/贴目/让子和引擎会话/条件匹配，不是前端给一个分数就可信。
- `buildReview`可处理合法的实战或变化前缀，但没有实战/变化来源身份；前后两份依据必须恰相邻且条件一致。
- 整局扫描已有前后证据引用；16现已补齐试下面板按完整规范前缀配对前后引用及本地依据查看，并明确试下来源。没有接入模型讲解或持久棋局/分支注册。
- 目前没有本机棋谱/聊天存档、精确回答缓存或在线教练；凭据/引擎设置保存不是这些能力。
- 证据当前为服务内存，最多2000条/64MiB序列化内容、签发后2小时及会话失效淘汰；恢复旧聊天不能直接复活旧依据。

## 后续设计必须覆盖的对话例子

1. 问实战某手：从同一落子前局面对照实战与引擎推荐，提供相应事实/估计/变化，不混用下一方候选。
2. 自由试下后追问：绑定试下起点、实际变化路径和当前分析，不套原谱结论。
3. 返回旧话题：找回对应原文及所讨论局面的有效依据，指代不清就澄清，依据失效就说明并重新取证。
4. 自动补查：局面/候选/PV数据必须来自受限工具与本地验证；模型只提出查询，不获得shell、任意URL、文件或凭据权限。工具具体集合、限额、费用请求数尚未定。

## 按chatbot主线修订的候选组合（具体机制尚未选定）

公开源码与RAG研究已完成，用户已明确聊天为主体。以下是主代理据此修订的组织建议，不是选型、实施或新增外发批准，也不以开源项目的功能清单代替验收。

不是Agent、RAG和Skill三选一，而是一个连续会话使用少量受限围棋能力：

1. 保留本项目已有棋规、KataGo管理、可信证据、凭据与发送授权设计，不搬外部项目整套执行权限或替换棋规；原费用预算设计已撤销。
2. 借鉴GoAgent的工具调用组织、kgteach的已分析/待分析/未知协议，以及Kifu-Sensei的前后证据与解释材料思路；已发现的分支/局面/标签缺口不能照搬。首版不引入shell、任意文件/URL、泛用MCP权限、外部项目的12轮默认值或自动重试。
3. 对话历史是主线：在模型容量及已批准字段内按时间顺序保留本盘对话，消息关联手数/分支，当前棋盘单独明确。不要预先裁成近期几轮再依赖检索恢复连续性；接近窗口上限时压缩较早讨论，保留近期原文、当前问题和局面依据，可回查本机完整原文。具体阈值与压缩实现仍待设计，不用金额阈值裁切或停止聊天。
4. Skill是任务方法的候选组织方式，如解释当前手、比较候选、核验试下：规定需要哪些依据、怎样核验、缺证据如何限制结论。工具执行实际棋规/引擎计算，Skill文本不扩大权限。RAG按需提供教材/概念材料，不替代对话主线或棋局计算。具体技能内容、何时加载、材料来源/许可、检索方式仍待设计，未选择向量数据库、远程embedding或具体摘要模型/实现。
5. 典型流程：连续对话＋当前棋盘 → 按问题选择必要的围棋任务方法 → 取得对应事实/分析及必要参考资料 → 在原会话中回答和追问。已有证据先由程序准备，必要时才在硬限额内补查合法变化；用户发送后，必要的模型续请求/摘要可在该问题的授权范围和运行硬限内自动完成，不再逐次弹窗；程序仍核验每次请求的范围、取消状态和局面身份，不因按问题授权就允许无限循环或越权。

开发字段类别、按本次提问授权以及接近窗口时压缩已确认；费用预算与超限默认暂停方案已撤销，仍待细化白名单schema、历史与工具结果保留规则、工具及次数/时间/长度硬限、迟到/失效处理后，才可形成完整聊天实施规格。没有开源代码或检索命中已经证明教练棋理可靠的结论。

## 历史：grill收口与coding agent参考研究

用户暂停了`implement-spec`，询问grill是否已经结束。当前完整连续聊天规格尚未收口，不能把16已验收或组合方向获准当作整份规格可实施。

用户针对剩余问题进一步说明：上下文压缩参考Claude Code等coding agent；会话恢复/在途回答处理也先参考其他agent；并要求解释“补查”含义。两路限定研究现已完成：[Claude Code官方文档/SDK边界](coding-agent-claude-context-research.md)，以及[Codex官方文档/固定发布提交实现](coding-agent-codex-context-research.md)。主代理复核了Claude Code核心压缩/恢复/队列文档及Codex压缩主体与相关入口片段，形成[综合建议](coding-agent-context-synthesis.md)。研究涵盖额外模型请求、失败、持久化/恢复/分叉、输入队列/中断及回复归属；Codex所查为v0.100.0历史快照，不代表最新版，未做运行或完整竞态审计。用户随后确认了上文四项交互决定；这是采用适合本产品的行为方案，不是照搬某个agent全部实现或阈值。

这里“本地变化补查”指教练为回答当前问题，请求棋规/引擎核验现有材料未覆盖的局面或变化，不是RAG查教材，也不是网页搜索。已有有效分析够用就复用；用户主动试下触发的现有分析，与未来模型主动发起的额外分析须区分。补查结果仍可能是有限搜索估计，不能把短PV或估值当作死活证明。具体工具及次数/时间/长度限制仍未定；用户本轮没有额外批准真实引擎运行。

这是研究与需求澄清，不启动新的应用实现、worktree或提交。逐请求确认已由用户明确改为本次提问授权；真实Key读取、真实传输和实际收费仍未获本轮执行授权。
